# CAPACITY CONNECT
## Backend Architecture & Implementation Specification
### Module 01 — Authentication & Identity Management

**Project:** Capacity Connect  
**Module:** Authentication and Identity Management  
**Architecture:** Modular Monolith  
**Backend:** NestJS + TypeScript  
**Database:** Neon Serverless PostgreSQL  
**ORM:** Prisma  
**Security:** Argon2id + Cloudflare Turnstile + JWT

---

# 1. OBJECTIVE

Build a secure, scalable authentication system for Capacity Connect.

The system must support three user roles:

1. ADMIN
2. TRAINER
3. TRAINEE

The authentication module is responsible for:

- User registration.
- Official IMD email domain validation.
- CAPTCHA verification.
- Secure password hashing.
- Login and logout.
- Email verification.
- Forgot and reset password.
- Access and refresh token management.
- Session management.
- Role-based authorization.
- Account status verification.

IMPORTANT: The existing React frontend has already been developed. Do not rebuild or redesign the frontend. Integrate the backend with the existing authentication screens and workflows.

# 3. ARCHITECTURE DESIGN

Implement a modular monolithic architecture.

Authentication must be separated into independent responsibilities.

Main components:

- Auth Module
- Users Module
- Roles Module
- Email Module
- Sessions Module
- Security Module
- Database Module
- Audit Module

Responsibilities:

**Auth Module:** Registration, login, logout, token refresh, password recovery.

**Users Module:** User account retrieval and basic identity information.

**Roles Module:** Role definitions and permission verification.

**Email Module:** Verification and password recovery emails.

**Sessions Module:** Refresh token storage, rotation and revocation.

**Security Module:** CAPTCHA verification, password hashing and security utilities.

**Database Module:** Prisma connection and database access.

**Audit Module:** Authentication event logging.

Do not combine all authentication logic inside a single service.

# 4. USER REGISTRATION

## 4.1 Registration requirements

Support registration for:

- Trainer
- Trainee

Public ADMIN registration must not be allowed.

Required registration information should match the existing frontend forms. Inspect the existing form fields before defining the final request DTO.

Minimum common fields:

- Full name
- Official email address
- Password
- Confirm password (frontend validation)
- Role
- CAPTCHA token

Role-specific profile fields should be handled through the appropriate profile workflow, not unnecessarily added to the authentication entity.

## 4.2 IMD official email validation

Only allow authorized IMD email domains.

Example:

- employee@imd.gov.in — Accept
- officer@imd.gov.in — Accept
- employee@gmail.com — Reject
- employee@fakeimd.gov.in — Reject
- employee@imd.gov.in.fake.com — Reject

IMPORTANT:

Do not assume that `imd.gov.in` is the only authorized domain. Confirm the official domain list with IMD administration.

Implementation requirements:

1. Normalize the email address.
2. Convert the domain to lowercase.
3. Extract the exact domain after the final @ separator.
4. Compare it against an explicit allowlist.
5. Reject unauthorized domains.
6. Never use substring matching.
7. Never trust frontend-only validation.

Store the approved domain list in backend configuration initially. Keep the design extensible for multiple approved domains.

Default policy: Both Trainer and Trainee registrations require an authorized IMD email address. Keep this policy configurable.

## 4.3 Registration workflow

1. User submits registration form.
2. Backend validates all required fields.
3. Backend validates the email domain.
4. Backend checks whether the email already exists.
5. Backend verifies Cloudflare Turnstile token.
6. Backend validates password requirements.
7. Backend hashes the password using Argon2id.
8. Backend creates the user record.
9. Account is created in PENDING_APPROVAL status.
10. Email verification is initiated.
11. User receives verification email.
12. User verifies the email address.
13. User remains pending until authorized admin approval.
14. Approved and email-verified users can log in.

Use a database transaction for operations that must succeed or fail together.

# 5. CLOUDFLARE TURNSTILE CAPTCHA

Integrate Cloudflare Turnstile.

Requirements:

- Frontend Turnstile widget.
- Backend token verification.
- Secret key stored only in backend environment variables.
- Site key exposed to the frontend through public configuration.
- Validate successful verification.
- Validate hostname against configured application domains.
- Validate the expected action where action metadata is configured.
- Reject expired and invalid tokens.
- Never trust CAPTCHA results supplied by the frontend without backend verification.

Backend verification endpoint:

`https://challenges.cloudflare.com/turnstile/v0/siteverify`

Apply CAPTCHA verification to:

- Registration
- Login
- Password recovery request

Do not treat CAPTCHA as a replacement for rate limiting.

# 6. PASSWORD SECURITY

Use Argon2id.

Requirements:

- Hash every password before database storage.
- Never store plaintext passwords.
- Never encrypt passwords for reversible storage.
- Never return password hashes through APIs.
- Use configurable Argon2id parameters.
- Benchmark the configuration on the deployment environment.
- Verify passwords using Argon2id verification.
- Rehash passwords when security parameters are upgraded.

Use the maintained Node.js Argon2 implementation.

Password policy:

- Minimum 12 characters.
- Maximum 128 characters.
- Do not silently truncate passwords.
- Reject known compromised passwords if a suitable password screening service is available.
- Never log passwords.

# 7. LOGIN AND AUTHENTICATION

## 7.1 Login workflow

1. User enters email and password.
2. User completes Cloudflare Turnstile.
3. Frontend submits login request.
4. Backend validates request fields.
5. Backend validates CAPTCHA.
6. Backend finds the user by normalized email.
7. Backend verifies password using Argon2id.
8. Backend checks email verification.
9. Backend checks account approval status.
10. Backend checks whether the account is suspended or rejected.
11. Backend generates access and refresh tokens.
12. Backend stores a hashed refresh token in the database.
13. Backend returns user identity and access token.
14. Refresh token is delivered using a secure HttpOnly cookie.

## 7.2 Account status rules

Maintain email verification and account approval as separate properties.

Account approval statuses:

- PENDING_APPROVAL
- ACTIVE
- REJECTED
- SUSPENDED

Email verification:

- emailVerifiedAt is null when unverified.
- emailVerifiedAt contains a timestamp when verified.

Login must be denied when:

- Email is not verified.
- Account is pending approval.
- Account is rejected.
- Account is suspended.
- Credentials are incorrect.

Return clear, frontend-compatible error codes.

Never allow a valid password to bypass account approval.

# 8. JWT AND SESSION MANAGEMENT

Implement two token types.

## Access Token

- Short-lived JWT.
- Recommended lifetime: 10–15 minutes.
- Used to authorize protected API requests.
- Contains user ID and role claims.
- Must not contain sensitive personal information.

## Refresh Token

- Recommended lifetime: 7 days.
- Delivered in Secure, HttpOnly, SameSite cookies.
- Store only its cryptographic hash in PostgreSQL.
- Rotate on every successful refresh.
- Revoke previous token during rotation.
- Detect refresh token reuse.
- Revoke the affected token family if reuse is detected.

## Logout

When the user logs out:

1. Revoke the current refresh session.
2. Clear the refresh cookie.
3. Reject future use of the revoked token.
4. Return logout success.

Support individual session revocation and logout from all devices.

Use a unique session identifier (`sid`) in access tokens where required for session-aware security.

# 9. EMAIL VERIFICATION

Implement email verification using secure, single-use verification tokens.

Requirements:

- Generate cryptographically secure random tokens.
- Store only token hashes.
- Set an expiry period, recommended 15–30 minutes.
- Invalidate tokens after successful verification.
- Prevent token reuse.
- Support resend verification.
- Apply resend rate limits.
- Never expose verification tokens in application logs.

Email verification must not automatically approve the account.

# 10. FORGOT PASSWORD AND RESET PASSWORD

## Forgot password

1. User enters email.
2. Complete CAPTCHA.
3. Backend checks the account.
4. Generate a secure random reset token.
5. Store its hash with an expiry.
6. Send password reset email.
7. Return the same generic response whether or not the email exists.

## Reset password

1. User opens the reset link.
2. Frontend submits token and new password.
3. Backend validates token.
4. Backend checks expiry and token usage.
5. Backend hashes the new password with Argon2id.
6. Backend updates the password.
7. Backend invalidates the reset token.
8. Backend revokes existing refresh sessions.
9. User must authenticate again.

# 11. DATABASE DESIGN — PRISMA + NEON

Use Neon PostgreSQL as the primary database.

Use Prisma for:

- Schema management.
- Database queries.
- Migrations.
- Relations.
- Transactions.

## 11.1 Initial database entities

### User

Fields:

- id: UUID
- fullName
- email (unique)
- passwordHash
- role
- accountStatus
- emailVerifiedAt
- createdAt
- updatedAt
- lastLoginAt

### RefreshSession

Fields:

- id: UUID
- userId
- tokenHash
- expiresAt
- revokedAt
- createdAt
- lastUsedAt
- userAgent (optional)
- ipAddress (optional, subject to privacy policy)

### EmailVerificationToken

Fields:

- id: UUID
- userId
- tokenHash
- expiresAt
- usedAt
- createdAt

### PasswordResetToken

Fields:

- id: UUID
- userId
- tokenHash
- expiresAt
- usedAt
- createdAt

### AuditLog

Fields:

- id: UUID
- userId (nullable for unauthenticated events)
- eventType
- ipAddress (subject to privacy policy)
- userAgent
- metadata (JSON)
- createdAt

### Role

Use a controlled role model supporting:

- ADMIN
- TRAINER
- TRAINEE

Avoid accepting arbitrary role names from registration requests.

## 11.2 Database rules

- Use UUID primary keys.
- Enforce unique email addresses.
- Add indexes to frequently queried fields.
- Use foreign key constraints.
- Use database transactions where necessary.
- Store timestamps in UTC.
- Never store plaintext tokens.
- Never store plaintext passwords.
- Use explicit deletion and retention policies for security records.

Do not create a second database or introduce MongoDB.

## 11.3 Neon configuration

Use separate Neon connection strings:

`DATABASE_URL`: Pooled Neon connection for normal application runtime.

`DIRECT_URL`: Direct Neon connection for schema migrations and administrative database operations where supported by the installed Prisma version.

Use the Prisma configuration appropriate to the installed version. Verify compatibility with Neon pooling before implementation.

Never commit connection strings or database credentials.

# 13. AUTHORIZATION AND ROLE-BASED ACCESS CONTROL

Implement NestJS Guards and role decorators.

Examples:

- ADMIN: Access to authorized administrative endpoints.
- TRAINER: Access to trainer-specific endpoints.
- TRAINEE: Access to trainee-specific endpoints.

Requirements:

- Validate JWT signature and expiry.
- Verify user account status for protected requests.
- Enforce permissions on the backend.
- Never trust role information sent from the frontend.
- Never allow users to change their own role.
- Restrict admin account creation to a trusted provisioning process.

Use database-backed roles and permissions or a controlled enum-based RBAC implementation initially. Keep the design extensible.
